# v0.5.0

If you are on 0.4, two things stop working when you upgrade.

- Six commands are gone: `ticket`, `grant-token`, `add-peer`, `pin`, `remove-peer`, `surfaces`.
  - Four take their place: `invite`, `accept`, `forget`, `key`. What `surfaces` printed is in `list`.
- `expose` will not run without a grantee. `expose 3000` on its own is an error; pass `--to <key>`, or `--all` for every peer the daemon knows right now.

The table has the replacement for each.

## Migrating

| Before | Now |
|--------|-----|
| `pai-sho ticket` | `pai-sho key`, or `pai-sho invite` for a one-time invitation |
| `pai-sho grant-token --label <name>` | `pai-sho invite --as <name>` |
| `pai-sho add-peer <key>` | `pai-sho accept <invite\|key>` |
| `pai-sho pin <key> --label <name>` | `pai-sho invite <key> --as <name>` |
| `pai-sho remove-peer <peer>` | `pai-sho forget <peer>` |
| `pai-sho surfaces` | `pai-sho list` |
| `pai-sho expose <port>` | `pai-sho expose <port> --to <key>` or `--all` |
| `pai-sho daemon -a <key> --enroll <token>` | `pai-sho daemon --accept <invite>` |

## Why the commands changed

The commands for linking two machines grew one release at a time. [0.1](https://github.com/cablehead/pai-sho/blob/v0.5.0/changes/v0.1.0.md) had `ticket` and `add-peer`: print your key, hand it over, the other side adds you. [0.3](https://github.com/cablehead/pai-sho/blob/v0.5.0/changes/v0.3.0.md) gave peers a stable identity, and two more ways to admit one: `grant-token`, a one-time code, and `pin`, for a key the host vouches for. By [0.4](https://github.com/cablehead/pai-sho/blob/v0.5.0/changes/v0.4.0.md) there were five commands for one job, and which ones you used depended on whether your machine was dialing or being dialed.

0.5 started from the flows, written down in `docs/scenarios.md` before any code changed, as the commands a person types, machine by machine. The one that showed the problem is a laptop reaching a shared build box, with the laptop's daemon already up and serving other peers. In 0.4 commands it goes like this. On the build box, run `ticket` and `grant-token`, and carry both values to the laptop. On the laptop, the only command that takes a token is `pai-sho daemon --enroll`, and the laptop's daemon is already running. `add-peer` takes a key and nothing else.

Linking two machines is one asking and the other agreeing. Hi, can we be friends? Yes, friends. None of the 0.4 names said that. `add-peer` read like it finished the job, and when the other side had not said yes, the only sign was a log line on its machine.

So the five commands became two, one for each half. `invite` asks, `accept` agrees, and nothing connects until both have run. The key and the code (0.4 called it a token) travel as one string, `key.code`, since a code was never any use without the key to present it to. The grant goes on the invitation: `invite --expose 8080` admits the laptop and grants it the port in one command, so there is no second step on the build box to forget. And each side picks what it will call the other, with `--as`. In 0.4 the build box had to name the laptop, with `grant-token --label`, and the build box is the side with no reason to type that name. The laptop is the one typing `buildbox.pai-sho:8080`.

`surfaces` and `list` printed overlapping JSON. `list` now has one row per peer with all of it.

I think this is much nicer to use, and hope you do too.

## Why `expose` changed

`expose 3000` on its own used to grant the port to every peer the daemon knew. The rule since [ADR 0001](https://github.com/cablehead/pai-sho/blob/v0.5.0/docs/adr/0001-directed-grants.md) is that a port is reachable only by the peers you grant it to. Leave `--to` off and the port went to every peer the daemon knew at that moment. That was the default, so adding a peer to reach its ports silently made it a recipient of every port you exposed afterwards. Now you name the grantee, with `--to <key>` or `--all`. `--all` grants to the peers the daemon knows at that moment, and a peer you admit later gets nothing until you expose to it.

## Highlights

- **Bare keys on both sides.** For a workload that cannot safely be handed a secret, such as a VM that takes its configuration on the kernel cmdline, where anything you put is readable: it generates its own keypair, the host reads off the public half and runs `invite <key>`, and the workload runs `accept <host-key>`. No code is minted and nothing secret travels into the workload ([ADR 0003](https://github.com/cablehead/pai-sho/blob/v0.5.0/docs/adr/0003-host-attested-enrollment.md), [ADR 0006](https://github.com/cablehead/pai-sho/blob/v0.5.0/docs/adr/0006-invitations.md)).

- **A pure core.** The decisions about who may connect and who may reach which port moved out of `peer.rs` into `src/core/session.rs`, a state machine with no IO that returns actions for the networking code in `peer.rs` to carry out. In `peer.rs` those decisions had no tests, because testing them meant two daemons and a network. Now they are unit tests that run in microseconds ([ADR 0007](https://github.com/cablehead/pai-sho/blob/v0.5.0/docs/adr/0007-pure-core.md)).

- **`list` says how each peer arrived**, by code or by key. By code means it held a one-time secret; by key means something vouched for that exact key. That matters when you are auditing who is on your network.

## Fixes

- A peer added while its daemon was down was lost. The dial happened before anything was recorded, so a failed dial left no peer and nothing to retry. The peer is recorded first now and the connection loop does the dialing, which also makes the first dial immediate instead of after a backoff.
- A port that failed to bind once stayed unreachable. The failure was logged and dropped, on the theory that the peer's next announce would retry it, but a peer whose ports do not change never re-announces. Binds now retry five times, 200ms apart.

## Tests

72 tests, up from 19. The 19 all lived in the modules with no networking in them, and deleting the authorization check in `peer.rs` would have kept them green. Unit tests in `core` now cover admission, grants, and tunnel authorization. `live_tests.rs` runs two real daemons over loopback with relays disabled, for dialing, reconnection, binding, and eviction. Replacing the grant check with `if true` fails five of them.

## Docs

- `docs/scenarios.md` works two flows end to end, a shared build box reached from a laptop and a laptop booting a vibenv, with the invariants each depends on.
- New ADRs 0006 (invitations) and 0007 (pure core). 0002 and 0004 carry notes where their vocabulary no longer matches what shipped.
- README, `--help`, and the crate description rewritten.
